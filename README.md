## Admin records and resident search

In Admin → Access, user search updates as the administrator types and returns matching resident, staff, and administrator names across zones. The resident portal's search is intentionally limited to public dashboard content; it does not expose other residents' account details.

The Admin → Access staff roster shows which staff portal sessions checked in within the last two minutes. Staff clients update their presence every 30 seconds while the page is visible, and the roster refreshes every 15 seconds. This is a recent-activity indicator, not a guaranteed real-time connection or proof of a person’s identity.

Approval history stays active for 30 days by default and older approvals are archived automatically when a new approval is recorded. Administrators can also archive approvals manually: the default is 30 days, and every manual archive requires confirmation. Setting retention to `0` archives every approval currently in the active list, including recent ones. Archives remain downloadable from Archived Files until an administrator explicitly deletes them.

## Resident registry

The staff portal's Resident registry shows resident totals for Zones 1–7; selecting a zone opens its paginated resident list. Full-name search can fill the exact birthdate and zone when it finds one exact match. Staff can add a person or an entire household through a three-step wizard, review possible duplicates, and edit resident details in the zone view. Names and zone are required for manual entries; birthdate, sex, marital status, occupation, address, and household ID are optional. Occupations accept suggested values or custom text. Sex may be left blank; the registry does not display an unclassified-sex category. CSV preview and import remain available, with imports accepting up to 500 rows per batch. New records remain pending verification. Staff can also create a persistent source-review warning for a purok/zone when source sheets are incomplete or unclear; open warnings remain visible until staff resolves them after reconciliation. Warning changes are staff-only and audited without storing resident names or free-form notes. Registry endpoints require an authenticated staff account, and responses are marked private and non-cacheable. The staff list returns only fields needed for registry work; address is retrieved only when a staff member opens the edit form or prepares individual-sheet printouts. Audit entries record who created, imported, verified, or changed a record without copying resident names or uploaded filenames into audit metadata. PostgreSQL writes and their audit entries are transactional; the JSON adapter serializes registry mutations. Duplicate review is checked again atomically at write time, and identical retries do not add duplicate records. The staff interface displays a privacy notice instructing users to use only necessary data for authorized duties and not share screenshots or exports outside approved work. The Node API initializes the PostgreSQL registry tables on startup. Before loading real resident data, confirm the office's authority, provide its approved privacy notice, establish least-privilege access and a retention schedule, and use the managed staff workflow rather than writing directly to the database.

Staff can print a full Zone 1–7 roster, family roster/individual sheets by household ID, one resident sheet, or a manually selected batch across zone pages. Print views are generated locally from authenticated registry responses and open in a separate print window; allow site pop-ups and use the browser print dialog to print or save as PDF. The staff Certificates & Printing center supports Barangay clearance, residency, indigency, and a manually editable custom template. A unique exact full-name match selects the registered resident automatically; ambiguous exact matches require staff to choose using birthdate and zone. Certificate printing is limited to active, verified residents. Certificate templates can use `{full_name}`, `{first_name}`, `{last_name}`, `{birth_date}`, `{zone}`, `{household_id}`, `{address}`, `{purpose}`, and `{issue_date}` placeholders. The standard certificates also support `{signatory}` and `{position}` placeholders; custom certificates do not include a signatory-name field and print a blank signature line labeled Barangay Captain/Punong Barangay. Custom wording is saved only in the current browser's local storage. Certificate output is a draft: staff must validate all statements, eligibility, purpose, and the issuing office's approved wording before signing or releasing it. The printer does not create issuance records or assign certificate numbers.

## Deployment

The current production frontend on Vercel uses the Node/Express API at `https://barangaylegaspi.onrender.com/api`, backed by PostgreSQL. Laravel is deployed as a staged migration target and is not yet the API used by the production frontend. Do not change `VITE_API_BASE` to Laravel until authenticated resident, staff, admin, and content-management workflows have passed a coordinated cutover check.

For a staged Hostinger migration of the Vite frontend, Node API, Laravel/PHP API, and PostgreSQL database, follow [the Hostinger deployment guide](./docs/hostinger-deployment.md). Laravel is not yet the active API and has incomplete API parity; keep it on an isolated staging database and keep current production services online until parity, restore, and rollback checks pass.

The VPS Compose stack is defined by `docker-compose.hostinger.yml` and `.env.hostinger.example`. It runs the existing Node API and Vite frontend against a private PostgreSQL container; the API uses same-origin `/api` routing. Laravel can be started only with the `laravel-staging` Compose profile and has a separate PostgreSQL volume. Do not expose Laravel to the frontend or migrate production traffic to it until route parity and isolated-data testing are complete.

1. Set the Vercel build command to `npm run build`.
2. Set `VITE_API_BASE` in Vercel to the active Node API URL ending in `/api`.
3. Keep the active Node/Express Render service connected to PostgreSQL and configure its keys, exact frontend `CORS_ORIGINS`, and other required environment variables. Use random keys of at least 32 characters. Existing installations must coordinate JWT rotation because it invalidates existing sessions; the MFA key-rotation procedure below preserves enrolled authenticators.
4. For a new database without an administrator, set `ADMIN_EMAIL`, `ADMIN_MOBILE`, and a strong `ADMIN_PASSWORD` on the active Node service before the first API login. Change that password after signing in.
5. The repository's `render.yaml` provisions the staged Laravel service and its connection to the existing Singapore PostgreSQL database; it does not configure or replace the active Node service. Back up the database and review the Laravel migration against a staging copy before any production cutover. Keep database credentials, application keys, and webhook secrets in deployment environment variables, never in source control.
6. Set `RESET_DELIVERY_URL` and `RESET_DELIVERY_TOKEN` on the active Node API to an authenticated HTTPS notification service before enabling password recovery. The service must accept a bearer token and the `password_reset` JSON payload; requests time out after 10 seconds.
7. For Admin-issued Staff temporary access, the same approved HTTPS delivery service must also support the `staff_temporary_access` event and deliver its `metadata.actionUrl` to the named recipient. Set `PUBLIC_APP_URL` to the official HTTPS portal origin if it differs from the current portal default. Do not enable the Admin control until the email template and link delivery have been tested with a non-production Staff account.

### Staff announcement publishing to Facebook and Messenger

The staff portal supports Facebook Page posts and Messenger announcements only. Configure these variables as secrets/environment settings on the active Node/Express Render service; never put Page tokens or app secrets in Vercel or source control:

- `META_PAGE_ID`: the official Barangay Legaspi Facebook Page ID. Do not use the currently linked Sangguniang Kabataan profile.
- `META_PAGE_ACCESS_TOKEN`: a Page access token with Meta's `pages_manage_posts` permission for Page publishing, `pages_messaging` for Messenger, and `pages_manage_metadata` to subscribe the Page to app webhooks.
- `META_APP_SECRET` and `META_WEBHOOK_VERIFY_TOKEN`: required to verify Messenger webhook deliveries.
- `META_GRAPH_API_VERSION`: a currently supported Meta Graph API version, in `vNN.N` format.

Configure the Meta app's Page webhook subscription for `messages` and `messaging_postbacks`, pointing to `https://barangaylegaspi.onrender.com/api/meta/webhook`. Publish the app and obtain any required Meta review/advanced access before enabling it for real residents. Staff can share the Page's Messenger link from the announcement form. A resident must start a Page conversation and send `SUBSCRIBE`; `STOP` or `UNSUBSCRIBE` opts them out. Subscriber Page-scoped IDs and consent state are stored by the active API.

Messenger delivery is restricted to opted-in people who messaged the Page within the preceding 24 hours. A correction is sent only to recipients who received that specific original Messenger announcement and who remain opted in and eligible; the API does not send a correction to a broader subscriber list. Facebook Page posts can be deleted from the staff portal; already-delivered Messenger messages cannot be unsent, so staff must publish a correction/retraction instead. Subscriber Page-scoped IDs and per-announcement delivery relationships are stored by the API to enforce these rules. Establish and publish an appropriate privacy notice and retention schedule for this data before enabling Messenger for residents. Verify the connected Page and permissions in Meta before setting the production environment variables.

The staged Laravel API preserves the `/api` routes and PostgreSQL data model, and runs its schema migration on container startup. The production health-check workflow monitors the active Node API and compares public announcement/event reads with the staged Laravel API.

For the active Node/Express API, automatic administrator seeding is only for a genuinely new database. If either configured seed identifier (`ADMIN_EMAIL` or `ADMIN_MOBILE`) already belongs to an account, seeding is skipped; it never promotes or overwrites an existing user.

The Laravel API does not create an administrator during login or from `ADMIN_*` environment variables. After deploying Laravel behind the intended HTTPS portal and configuring its isolated database and verified Resend sender, an authorized operator can issue the first Laravel Admin setup invitation with `php artisan app:invite-admin admin@example.gov --confirm`. The invite is single-use, expires after 12 hours, stores only a token hash, and lets the recipient choose their password. The invitation URL is emailed and never printed. The existing GitHub operator-account workflow still provisions accounts through the active Node API; do not confuse it with this Laravel CLI command.

The Node/Laravel API route parity gate is `npm run check:laravel-parity` and must report zero missing routes before a replacement can be considered. Route coverage alone is not sufficient: run the Laravel suite, validate behavior and integrations against an isolated database copy, and complete deployment/rollback checks first.

#### Operator account provisioning

Admins can create Admin or Staff accounts directly in the authenticated portal; Staff members can create Staff accounts only. Portal users cannot create or promote Super Admin accounts. The API generates a strong temporary password, displays it once to the creator, and requires the account holder to change it before accessing any other portal features. The account holder can change their password later from Settings. Share temporary passwords only with the account holder through a secure channel.

Protected operator invitations remain available for initial or fallback Admin, Staff, and Super Admin provisioning. These operator invitations are single-use, expire after 12 hours, store only a token hash, and let invitees choose their own password during acceptance. Configure `RESEND_API_KEY` and a verified `SUPER_ADMIN_INVITATION_FROM_EMAIL` on the active Node/Express Render service before using them. Set `PUBLIC_APP_URL` to the production portal's HTTPS origin if it differs from the default. Do not place these values in source control or expose invitation links in logs. The `render.yaml` blueprint describes the staged Laravel service; it does not configure the active Node API.

If no Admin can issue the initial invitation, an authorized deployment operator can use the following commands in the active production Node service environment with its PostgreSQL connection. Never run them against a local or staged database to provision live accounts.

- To promote an existing, verified resident account, run `npm run accounts:promote-admin -- --confirm`. The command changes the role only when `ADMIN_EMAIL` and `ADMIN_MOBILE` match the same active resident account, records an audit entry, and never changes the password or other profile fields. It refuses mismatches, unverified or disabled accounts, and non-resident roles. If the account is already an administrator, it makes no changes.
- If no existing verified resident can be promoted, choose `invite-admin` in the protected production account workflow and provide the intended Admin's email, leaving mobile empty. The operator-only `npm run accounts:invite-admin -- --email admin@example.gov --confirm` fallback sends a single-use Admin setup link. The invitee verifies the email, enters their name and mobile number, and chooses their own password; no initial password is generated or shown to the operator. Use this to bootstrap the first Admin, then create further Admin or Staff accounts from the portal.
- The `npm run accounts:invite-staff -- --email staff@example.gov --confirm` command is an operator-only fallback. The position defaults to `Staff`; provide `--position "Secretary"` when authorized. It requires the configured Resend API key and verified invitation sender, emails an audited, single-use invitation expiring in 12 hours, and never prints the raw invitation URL. If delivery fails, the invitation is revoked and audited.
- The invitee completes `/staff-invite` on the production portal, confirms their name and mobile number, and chooses a password. The staff account is created only when the invitation is accepted. Token hashes, not raw tokens, are stored. Reissuing an invitation revokes any prior unused invitation for that email.
- Admins may issue a single-use temporary access email to an existing active Staff account from Admin → Access. The link is valid for 15 minutes, invalidates any prior unused link for that account, retains the Staff role, and honors that account's existing MFA. The API stores only a hash of the link token; if delivery fails, it revokes the grant. The notification service must implement `staff_temporary_access` and include `metadata.actionUrl` in the email; an HTTP success response alone does not prove that an email reached its recipient.

The production schema is initialized by the Node API at startup. This feature adds the `staff_temporary_access_grants` and `official_profiles` tables without changing existing user or request data. Deploy this code and wait for a healthy service before using portal account creation or operator provisioning. The operator commands do not initialize the schema or run the administrator seed, preventing unrelated startup writes. Never pass passwords, database URLs, or invitation tokens as command-line arguments.

#### Super Admin role assignment

`super_admin` is a distinct account role. It retains the existing Admin API and dashboard access and adds a read-only system-monitoring view; regular Admin accounts cannot open that view or modify Super Admin profiles. Portal users cannot promote or change the role of an existing account; Super Admin setup invitations remain operator-only. Regular Admins can create new Admin or Staff users, while Staff can create Staff only; all portal-created accounts receive a one-time temporary password and must change it at first sign-in. To upgrade an existing account, promote only an active, verified resident whose email and mobile both match. To create a new Super Admin account, issue a protected one-time setup invitation: the invitee confirms their name and mobile and chooses their own password at `/super-admin-invite`. The system stores only the invitation-token hash and the password hash. Invitations expire after 12 hours and can be accepted once.

The protected `Production account role assignment and invitations` GitHub Actions workflow can promote an existing resident to Admin or Super Admin, or email a one-time Admin, Staff, or Super Admin setup invitation. It runs only when manually dispatched from `main`, uses the `production` environment, and requires the environment variable `PRODUCTION_ACCOUNT_WORKFLOW_ENABLED=true`. Configure that environment with required reviewers and the `PRODUCTION_DATABASE_URL` and `PRODUCTION_JWT_SECRET` secrets before enabling the workflow. Admin, Staff, and Super Admin invitations additionally require a `RESEND_API_KEY` secret and a `SUPER_ADMIN_INVITATION_FROM_EMAIL` variable. Verify the sender address/domain with Resend before configuring it. The workflow sends invitation links through Resend's HTTPS API and never prints links or request payloads in Actions logs.

Choose `invite-staff` to send a Staff invitation; provide the intended account holder's email, leave mobile empty, and optionally provide the Staff position. The email must not already belong to a portal account. Choose `invite-super-admin` for a Super Admin setup invitation; if its email already belongs to an account, use `promote-super-admin` with both matching identifiers for an active, verified resident. The workflow sends single-use, 12-hour setup links using the configured Resend sender and never prints links in Actions logs. Invitees enter their name and mobile and choose their own password. Reissuing an invitation revokes the previous unused link. Account creation and invitation acceptance are recorded in the audit log.

Choose `invite-admin` to bootstrap an Admin account when there is no existing verified resident to promote. Provide the intended account holder's email and leave mobile empty; the invitee confirms their name and mobile and chooses a password through the one-time link. If the email already belongs to a verified resident, use `promote-admin` with both matching identifiers instead.

### Mau assistant maintenance

Mau currently uses client-side, keyword-matched responses; it is not a machine-learning model and does not continuously train on conversations. Adapt it through staff-approved, version-controlled FAQ updates: maintain role- and language-specific intents in `src/mau-responses.js`, keep English and Filipino answers aligned in `src/translations.js`, and add question, role, language, and out-of-scope coverage in `tests/translations.test.js`. Recheck these answers whenever a portal workflow or policy changes, and keep claims about unavailable features explicit.

Do not collect or use resident conversations for training without an explicit privacy review, user notice and consent, retention limits, and a human review process for proposed answer changes.

The Captain, Secretary, and Treasurer public profiles are editable in Staff/Admin → Officer profiles. Staff and Admin may update public names, photos, profile links, and up to eight separate community links; resident accounts cannot. Existing single group links are retained when the community-link list is first introduced. All profile details start blank until filled in. Profile and community links are optional HTTPS URLs. Admins can also change the system logo from Officer profiles; the logo is used across the portal and falls back to the bundled seal when no custom logo is available.

Official photos and the system logo are uploaded directly from the admin portal to S3-compatible object storage using short-lived, size-limited upload policies; the API does not buffer image bytes. Configure `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_REGION`, `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_ACCESS_KEY_ID`, and `OBJECT_STORAGE_SECRET_ACCESS_KEY` on the Express API. Set `OBJECT_STORAGE_FORCE_PATH_STYLE=true` only if required by your provider. Scope the storage credentials to the `official/` and `branding/system-logo` prefixes, configure bucket CORS to allow `POST` from the web app’s exact origin, and add lifecycle rules to remove stale objects under each `official/<role>-portrait/pending/` and `branding/system-logo/pending/` prefix. Keep the bucket private; the API issues short-lived signed read URLs. Uploads accept JPEG, PNG, and WebP images up to 5 MB and validate the file signature before publishing. Without these settings, the image controls report that storage is unavailable.

Payment records remain empty until a real billing/payment source is integrated. The previous API's hard-coded invoice examples were demonstration data, not resident charges; neither API should create or display them as real payments.

Keep the Vercel `VITE_API_BASE` pointed at the existing Node API until authenticated resident, staff, and administrator workflows have been verified against Laravel. Until that cutover, Laravel's public announcement and event reads use `PUBLIC_CONTENT_API_BASE` to read from the Node API, and Laravel returns `502` rather than a misleading empty collection if the source is unavailable. Announcement writes on Laravel return `409` during this transition so content is not silently written to a database the active portal does not read. Do not cut over until the resident, staff, administrator, and content-management workflows have been migrated and verified together.

### Coordinated MFA/JWT key rotation

Node-issued sessions are signed with `JWT_SECRET` and expire after seven days. Do not accept tokens signed with a compromised previous key during rotation. Existing MFA secrets are stored as `v1` ciphertext encrypted using the JWT key; both APIs support a separate `MFA_ENCRYPTION_KEY` and `v2` ciphertext for a controlled migration. A temporary, comma-separated `MFA_ENCRYPTION_KEY_PREVIOUS` list supports deployments whose services currently use different MFA keys while records are being re-encrypted.

If only `MFA_ENCRYPTION_KEY` is exposed, follow the MFA re-encryption steps below but do not rotate `JWT_SECRET`; changing the JWT key invalidates sessions and is unnecessary unless the JWT key itself is compromised or rotation is separately planned.

1. Back up PostgreSQL and verify the backup before changing service secrets.
2. Deploy the backward-compatible API code while leaving `MFA_ENCRYPTION_KEY` unset. Confirm the production API remains healthy.
3. Preserve each service's existing MFA key. Set `MFA_ENCRYPTION_KEY_PREVIOUS` on both services to a comma-separated list containing both existing keys and a new, distinct random key. Keep each service's current key unchanged and deploy this staged configuration first; this ensures either service can read existing ciphertext and ciphertext written with the new key during rollout.
4. Set the same new key as `MFA_ENCRYPTION_KEY` on both services, retaining both old keys in `MFA_ENCRYPTION_KEY_PREVIOUS`, and deploy. Keep the current JWT key temporarily so `v1` records and sessions remain readable; new MFA records are written as `v2` using the shared key.
5. In the active Node service environment, run `npm run mfa:rotate-key` to validate records without changing them. Review only the record counts. After verifying a backup, run `npm run mfa:rotate-key -- --apply`; it re-encrypts both `v1` and old `v2` records and verifies every record with only the new key. Remove `MFA_ENCRYPTION_KEY_PREVIOUS` from both services after confirming the deploy. The command never prints decrypted values and detects concurrent edits.
6. Replace `JWT_SECRET` with a new random value on the Node service and redeploy. This intentionally invalidates all existing JWT sessions; users sign in again. Do not configure a previous-key JWT fallback.
7. Configure Laravel with the same new `JWT_SECRET` and `MFA_ENCRYPTION_KEY`, then validate representative login and MFA flows before any frontend cutover.

Keep Node serving traffic until rotation, database checks, and Laravel verification all pass. Never paste key values into logs, source control, or chat.

Vercel continues to serve the frontend and SPA routes through `vercel.json`.

### Production health monitoring

The `Production health check` GitHub Actions workflow checks the public frontend, Laravel API, PostgreSQL-backed health endpoint, and public services, announcements, and events endpoints every 15 minutes. It also runs after changes to the workflow and can be started manually from the repository's Actions tab. A failed check identifies the failing service in the workflow log.

Enable GitHub Actions failure notifications in your GitHub account or repository notification settings to be alerted when a scheduled check fails. The frontend reports rendering errors, uncaught browser errors, and unhandled promise rejections to the active API. Reports are rate-limited and contain only an allowlisted event type, route, language, and role; error messages, stacks, and account data are deliberately excluded. Review these warnings in the active API service logs. The frontend also shows a bilingual recovery screen if a rendering error prevents the portal from loading.

These checks cover uptime and public read paths; they do not replace authenticated workflow tests, application-log review, or verified database backups.

The admin portal health card checks API availability and, for PostgreSQL deployments, database connectivity. It does not inspect backup schedules, alert delivery, restoreability, or staff coverage. Verify automated database backups and perform a restore test separately. Admin → Access is for monitoring and account details; only an authorized deployment operator can provision an administrator or issue a staff invitation.

### Staff request dashboard metrics

The staff request dashboard reads request totals from the authenticated staff dashboard API. Pending review counts only `Pending`; in-processing counts only `In Review`. Needs-information requests remain a separate attention category. The request table is filtered, sorted, and paginated by the API, with date filters interpreted in `Asia/Manila`.

The staff Reports tab supports Manila-time reporting periods and custom date ranges, request-type and current-status filters, status/type breakdowns, activity trends, decision metrics, and CSV export. The report opens with three large summary counts; filters and detailed analytics are progressively disclosed to reduce visual overload. Received totals and status breakdowns are based on submission dates; decision metrics are based on recorded decision dates. Report responses and exports omit resident contact details. The current request workflow has no release/completion state, processing deadline, or staff assignment field, so reports do not estimate release or overdue metrics or treat `Approved` as completed. Residents are told that approval is not confirmation of document release. Staff can archive approved/rejected requests older than 30 days or explicitly archive all processed requests; both actions require confirmation, and resulting archives remain available in Archived Files for viewing or download. Average response time is not reported because the request model does not persist a reliable first-response timestamp. Add these workflow fields and guarded transitions before enabling those metrics.

Administrators can maintain a resident's household ID, address, family count, and household-member names and relationships from the resident detail editor. These details remain attached to the resident account; a separate household registry, multi-head household workflow, and Laravel API parity are not yet implemented.

## Local development

Install Node.js dependencies from the repository root with `npm install`, then run `npm run dev`. The Vite frontend runs on port 5173 and the local Express API runs on port 3001, using the local JSON store unless `DATABASE_URL` is configured. Do not point local development or tests at the production database. Run `npm test` and `npm run build` before submitting changes.

The Node API request workflow stores the resident's online/physical copy choice, status history, and staff notes. Staff can request missing information; a resident follow-up returns that request to review. The resident request page and staff queue show the same status timeline. Browser reminders are scoped to the signed-in resident and can alert while the app is open; they are not push notifications when the browser is closed. Announcement channel selections are planning metadata only until official social accounts are connected; the app does not claim to publish posts automatically.

The Express API uses JSON storage only when `DATABASE_URL` is absent in local development. When PostgreSQL is configured, database errors fail the affected operation; records are not silently written to a parallel JSON file. Production Express startup requires `DATABASE_URL`. Local JSON data is not synchronized with PostgreSQL and must not be treated as a database backup. The JSON adapter strips legacy plaintext `password` fields when reading and writing user records; only password hashes are retained.

Empty reports, announcements, and event lists are returned as empty until actual records are entered. The former demonstration reports and sample announcements/events were removed so they cannot be mistaken for barangay records. Events currently have no persistent management workflow.

Do not upload official scans to the current local JSON store or use the empty payment screens for real transactions. Document storage needs an access-controlled persistent storage design, while real payment recording needs an agreed reconciliation workflow. Keep Laravel cutover and production key changes paused until there is a verified database backup and restore.

To run the Laravel API locally instead, install PHP 8.2 or newer with the `pdo_sqlite` extension and Composer. In `laravel-api`, install Composer dependencies, copy `.env.example` to `.env`, run `php artisan key:generate`, create `database/database.sqlite`, then run `php artisan migrate`. Start it with `npm run dev:api` from the repository root and set the Vite API base to `http://localhost:8000/api`. Configure PostgreSQL instead of SQLite only with a non-production development database.
